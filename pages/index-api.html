AIDA API

A AIDA API levará a mesma análise da plataforma para dentro de outros sistemas: uma imagem entra, um resultado estruturado sai — com os mesmos estados, as mesmas ressalvas e as mesmas evidências que a interface mostra hoje.

Não há endpoints públicos abertos

Não existe cadastro, chave de acesso nem domínio público de produção. Os exemplos desta página são conceituais e servem para descrever o formato pretendido.

POST /v1/analyze/image
200 OK "result": … "ai_probability": … "confidence": …
Objetivo

Integrar a análise, sem reescrevê-la.

Hoje a análise só existe dentro da interface do AIDA. Quem precisa verificar imagens dentro do próprio fluxo — um sistema de redação, uma plataforma de denúncias, uma ferramenta de moderação — precisaria replicar o pipeline. A API existe para evitar isso: o mesmo núcleo, exposto por HTTP, com um contrato estável.

Contrato

Três estados, sempre

A resposta preserva REAL, IA/MANIPULADA e INCONCLUSIVO. Integrações binárias rotulariam como IA justamente o que o sistema declarou indeterminado.

Evidência

Não é só um número

Scores por módulo, indicadores de qualidade, limitações do arquivo e os mapas visuais acompanham o resultado, como já acontece na interface.

Ressalva

Obrigatória na saída

O campo de ressalva viaja junto com o resultado e não deve ser omitido por quem integra: o retorno é indício técnico, não prova.

Demonstração conceitual

O formato pretendido.

O par abaixo ilustra a forma da chamada e da resposta. O host é fictício, não há chave real e os valores servem apenas para mostrar a estrutura — nenhum deles vem de uma análise.

Requisição conceitual 
POST /v1/analyze/image
Host: api.exemplo.aida
Content-Type: multipart/form-data
Authorization: Bearer <sua-chave>

# campos do formulário
image=@foto.jpg
evidence=true
Resposta conceitual 
{
  "result": "INCONCLUSIVO",
  "confidence": "baixa",
  "module_scores": { … },
  "quality": { … },
  "limitations": [ … ],
  "evidence": { … },
  "disclaimer": "indício, não prova",
  "analysis_id": "<id>"
}

O exemplo mostra deliberadamente o estado indeterminado: é o caso que integrações costumam esquecer de tratar.

Arquitetura futura

Uma camada fina sobre o Core.

A API pública não conterá lógica de detecção. Ela recebe a requisição, valida, delega ao AIDA Core e devolve o resultado no contrato versionado — a mesma separação que já existe entre a interface e o pipeline de análise.

Camada 01

Borda HTTP

Autenticação por chave, limites de uso, validação de formato e tamanho do arquivo.

Camada 02

Orquestração

Fila para requisições longas, cache por conteúdo e reaproveitamento entre chamadas.

Camada 03

AIDA Core

Extração, módulos de detecção, fusão calibrada e política de decisão — sem duplicação.

Camada 04

Contrato versionado

Resposta em /v1, com mudanças incompatíveis reservadas a uma versão nova.

Casos de uso

Quem ganharia com a integração.

Redações e checagem

Verificar imagens recebidas dentro do próprio sistema editorial, antes da publicação.

Moderação de conteúdo

Marcar para revisão humana os envios com indícios mais fortes, sem decidir sozinho.

Pesquisa acadêmica

Rodar o pipeline sobre conjuntos grandes e comparar resultados de forma reprodutível.

Ensino

Construir exercícios que consomem a análise e discutem por que ela às vezes se abstém.

Roadmap

Etapas previstas.

Nada disso está implementado como produto público. A ordem segue a dependência entre as etapas, e nenhuma delas tem data.

  1. 01

    Endpoint de imagem

    POST /v1/analyze/image com contrato estável e os três estados de resultado.

    Planejado
  2. 02

    Chaves de API

    Emissão, rotação e revogação de chaves, com escopo por aplicação.

    Planejado
  3. 03

    Autenticação

    Verificação da chave na borda e vínculo entre chamada, aplicação e responsável.

    Planejado
  4. 04

    Limites de uso

    Cotas por chave e janela de tempo — a análise é cara e precisa de proteção contra uso em rajada.

    Planejado
  5. 05

    Documentação

    Referência gerada a partir do próprio contrato servido pela API, para não descolar do código.

    Planejado
  6. 06

    Logs

    Registro de chamadas para auditoria e diagnóstico, com retenção declarada no aviso de privacidade.

    Planejado
  7. 07

    Monitoramento

    Disponibilidade, latência por etapa e alerta quando um módulo do Core deixar de carregar.

    Planejado

Enquanto a API pública não existe, a análise continua disponível pela interface do AIDA Image.
